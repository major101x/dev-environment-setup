# CONTEXT.md

## Glossary

| Term | Definition | Avoid |
|---|---|---|
| **Profile** | Named preset that pre-checks a set of Tools (e.g. `default`, `go`, `rust`, `fe`, `be`, `python-ai`, `ai-agents`, `full-stack-web`). Selecting a Profile does not lock choices — the user can still uncheck individual Tools. A Profile expands to its Tools at two different *moments*: pick time in the TUI (toggling its row checks them in the list) and parse time on the CLI (`--profile=go`). Same Tools either way. | Bundle, preset (use Profile) |
| **Tool** | Installable unit the user selects: an apt package, a language toolchain, a binary, or a service (e.g. `gh`, `fastfetch`, `opencode`, `node`, `puppeteer`, `docker`, `exa-mcp`, `pocock-skills`, `pip`). A Tool is what appears in the picker and in a Profile. It is **not** the unit of installation work — see Install Step. | App, library, package |
| **Install Step** | The unit of installation work: one idempotent function that delivers one or more Tools. The mapping is many-to-one — `install_go` delivers `go`, `golangci-lint` and `air`; `install_node_and_puppeteer` delivers `node` and `puppeteer`. An Install Step is what carries progress, a lifecycle state and a result, and so what gets a row on the install screen, labelled by the Tools it delivers. | Job, task, package, install function |
| **Prerequisite** | A Tool an Install Step needs on the machine before it can do anything: `install_jupyter` needs `pip`, `install_qdrant` needs `docker`. Declared per Install Step (`STEP_REQUIRES`) because that is the unit that runs, and read three times — resolution adds a prerequisite that is neither picked nor present to the Toolset, the picker's panel shows that addition before ENTER and names the dependent a Declined prerequisite would strand, and the run-time gate names the one that still is not there as the detail on `skipped`. Met means on the machine already *or* delivered by a Step that has run and landed. See [ADR-0014](docs/adr/0014-resolution-adds-a-missing-prerequisite-to-the-toolset.md). | Dependency (the *state* is `unmet dependency`; the Tool is a Prerequisite), requirement |
| **Declined prerequisite** | An auto-added Prerequisite the user unchecked in the picker before confirming. The picker shows the closure resolution would perform, marks an addition `[+]`, and allows TAB on it — Profiles are presets, not locks, and an addition nobody asked for is no more a lock than a Profile is. The decline is a pick: it leaves the picker with the checks, is saved to `config.json` so `--replay` reuses it, and resolution honours it instead of adding the Tool back. Its dependent is *not* unchecked — it is marked unsatisfiable in the panel and reaches `skipped — unmet dependency` in the run. See [ADR-0015](docs/adr/0015-the-picker-shows-the-closure-and-a-decline-is-a-pick.md). | Conflict, override, exclusion |
| **Lifecycle** | The seven states an Install Step moves through: `queued` → `downloading` → `installing` → `done`, plus the three terminal states that carry what the happy path cannot — `already installed`, `skipped` (detail names the unmet dependency) and `failed`. [ADR-0005](docs/adr/0005-install-progress-is-phases-not-byte-level.md) calls the four transit states **phases** — those are what an installer reports about itself; the three terminal states are only ever states, and the runner alone decides them. Not every Step passes through `downloading`: only the three with a separable download do. | Job status, progress bar |
| **Version probe** | The command a Tool answers its version with, declared per Tool in `TOOL_VERSION` and defaulting by convention to `<tool> --version`. Declared because the convention is wrong for most of the interesting Tools — the binary is named otherwise (`pip3`, `rustc`), the flag is its own (`go version`, `node -v`), or the binary is not on the run's PATH yet, which is routine for a Tool this run has just installed. The answer is the word carrying the number, so `go1.23.4` and `v22.11.0` keep the prefix their tool printed; a probe that answers no version reports `(unknown)`, and the two Tools with genuinely none — the skills bundle (a count of files) and the Exa MCP registration — are declared `none` and report `installed`. `done` and `already installed` carry the result as their Transition detail, one version per Tool the Install Step delivered. A dry run executes no probe and reports `(dry run)`. See [ADR-0016](docs/adr/0016-a-tool-reports-its-version-from-a-declared-probe.md). | Verification (that was the trailing second pass, deleted by #25), check |
| **Transition** | One state change, emitted as one plain-text line on stdout: `[STEP] <install step> \| <state>[ \| <detail>]`. The transition stream is the run made observable — the install screen is drawn from it, a pipe reads it as it stands, and the tests assert against it through the process boundary. See [ADR-0011](docs/adr/0011-the-lifecycle-is-a-plain-text-transition-stream.md). | Event, log line, message |
| **Log** | The run's written record at `setup.log`, in plain text: its own narration, every Transition, and everything an Install Step said while it ran — installer chatter and this script's lines from inside it alike — inside a delimited **section**, `[STEP OUTPUT] <install step> \| begin` … `\| end \| exit <status>`. Written line by line by the run, not by a blanket `tee` redirect: that frees the terminal for the install screen and stops a re-entrant subcommand's stdout going to the log instead of to its caller. A Step's output goes to the log and not to the terminal, which keeps the Transition stream instead. See [ADR-0012](docs/adr/0012-the-log-is-written-per-install-step.md). | Transcript, output |
| **Summary** | The end of a run, in two parts: one counts line over the terminal states of every planned Install Step (`9 install steps: 6 done, 1 already installed, 1 skipped, 1 failed`), then one line per failed Step naming the Tools it owed and why it failed. Printed last, before anything reads stdin — a run that carries on past a failure ([ADR-0006](docs/adr/0006-a-failed-install-step-does-not-abort-the-run.md)) has scrolled the failure away by the time it ends, and this is where it comes back. It is also what makes the exit status explicable: any Step in `failed` means exit 1, and `skipped` is not a failure. | Verification (deleted), report, results |
| **Snapshot** | Everything a frame of the install screen varies on, as one `<kind> \| <fields>` line per item: every Install Step with its label, state, detail and the tail of what it said, the run's elapsed time, the active Step's, a spinner tick, and whether the frame is final. The live screen builds it from the Transition stream; `setup.sh __render WIDTH HEIGHT < snapshot` builds it from a file. A frame is a pure function of a Snapshot and a terminal size, which is what makes it assertable exactly. | State, model |
| **Frame** | One paint of the install screen: a bordered box holding a counts line, a grid with one cell per Install Step, the Step in flight, then a failure board ([ADR-0007](docs/adr/0007-the-install-screen-is-a-grid-of-every-install-step.md)). A live Frame is padded to the terminal height because it is repainted in place; the finalised Frame is printed once, so it runs to its natural length. | Screen (that is the whole thing), view |
| **Install screen** | What a run looks like on a terminal: one Frame repainted in place from the Transition stream, by a reader process on the other end of it, from the first Install Step to the last. It finalises in place and the Summary is printed beneath it, before anything reads stdin. Up only when stdout is a terminal and the Log is open; a pipe gets the plain stream. See [ADR-0013](docs/adr/0013-the-install-screen-reads-the-stream.md). | Progress bar, dashboard, TUI (that is the picker) |
| **Category** | UI grouping for Tools: `Languages`, `Frontend`, `Backend/DB`, `AI/ML`, `Infra/DevOps`. Categories are collapsible and searchable but do not affect install logic. | Group, section |
| **Toolset** | Concrete set of Tools resolved from selected Profiles + manual toggles. Saved to persistence. | Stack |
| **Default Toolset** | The 11 Tools pre-checked when no Profile is chosen — the `default` Profile: `gh`, `fastfetch`, `opencode`, `node`, `puppeteer`, `chrome`, `docker`, `pip`, `eza`, `exa-mcp`, `pocock-skills`. (Counted as 9 originally, when `node`/`puppeteer`/`chrome` were one line and `eza` was unlisted.) | Base, minimal |
| **Persistence** | File `~/.config/dev-setup/config.json` that stores last Toolset and flags for `--replay`. | Cache, state |
| **TUI** | Interactive picker built on `fzf` >= 0.60 (needs `--input-border` and `click-header`). Tabbed by Category (`All`, `Languages`, `Frontend`, `Backend/DB`, `AI/ML`, `Infra/DevOps`), with a live Selected Toolset panel. Auto-installed if absent or too old; apt's 0.44.1 does not qualify. Not a hand-rolled bash `select`, and no longer `gum`. | UI, wizard |

## Decisions

- **Decision: Single-context repo** — per `docs/agents/domain.md`, this repo uses one `CONTEXT.md` at root + `docs/adr/` for ADRs.
- **Decision: Interactive by default** — `./setup.sh` with no args launches TUI; flags `--yes`, `--profile=`, `--all`, `--no-auth`, `--search=`, `--replay` enable non-interactive/CI use. `gh auth login` stays last and is skipped with `--no-auth`.
- **Decision: Profiles are presets, not locks** — checked items from a Profile remain uncheckable (user can customize even with recommended).
- **Decision: LTS everywhere** — language toolchains use `lts/*` (node via nvm, go latest, rust stable, python 3.12). Toolchain `PATH`/`~/.bashrc` mods are offered as opt-in prompt inside TUI.
- **Decision: fzf is the TUI, gum removed** — `gum filter` has no `--border`, `--padding` or key-binding flags, so its "tabs" were a static header string that could never show an active state. fzf provides `--input-border`, `--bind left/right/click-header` and `transform-header`. `ensure_fzf` capability-checks (apt ships 0.44.1, which lacks them) and installs 0.74.3 otherwise. Supersedes the earlier "gum primary, fzf fallback" decision. See [ADR-0002](docs/adr/0002-fzf-with-a-version-floor-replaces-gum.md).
- **Decision: TUI rows are typed by marker glyph** — `◆` Profile / `·` Tool, because `go` and `rust` are each both a Profile key and a Tool key and name lookup mistyped them. See [ADR-0003](docs/adr/0003-tui-item-type-comes-from-the-marker-glyph.md).
- **Decision: Persistence opt-in automatic** — every interactive run writes `~/.config/dev-setup/config.json`; `--replay` reuses it.
- **Decision: `full-stack-web` is a composite alias** — it resolves to `fe + be + docker + chrome + node`, deduplicated, rather than owning its own Tool list, so a Tool added to `fe` or `be` reaches it. Composition is this one alias's mechanism, not a general one: `ai-agents` restates `python-ai` on purpose. `c-build` is not part of it. See [ADR-0001](docs/adr/0001-full-stack-web-is-a-composite-alias.md).

- **Decision: Install Step is the unit of installation work** — the user picks Tools, but installers are many-to-one, so progress, state and results attach to Install Steps. See [ADR-0004](docs/adr/0004-install-step-is-the-unit-of-installation-work.md).
- **Decision: install progress is phases, not byte-level bars** — only 2 of 27 Tools have a measurable discrete download. See [ADR-0005](docs/adr/0005-install-progress-is-phases-not-byte-level.md).
- **Decision: a failed Install Step does not abort the run** — mark failed, continue, summarise at the end. The summary is the counterpart of continuing: counts of every terminal state, then each failed Step named with the Tools it delivers and why, printed before anything reads stdin. Its consequence ships with it — a run holding any failed Step exits 1, while `done`, `already installed` and `skipped` all exit 0, because CI reads the exit status and nothing else. See [ADR-0006](docs/adr/0006-a-failed-install-step-does-not-abort-the-run.md).
- **Decision: the install screen is a bordered grid of every Install Step** — a content-height box with one grid cell per Step, then the Step in flight, then a failure board. Nothing is collapsed or scrolled; it spends terminal width rather than height. Live frames are padded to the full terminal height because they are repainted in place; the finalised frame is printed once, so it is neither padded nor capped and runs to its natural length — which is what buys a version on every cell, and what stops the failure board being cut off. See [ADR-0007](docs/adr/0007-the-install-screen-is-a-grid-of-every-install-step.md).

- **Decision: the fzf callbacks are the test seam** — `bats` drives `setup.sh __tui_*` directly, because fzf reads `/dev/tty` and no piped stdin can drive the picker itself. The callbacks are also where the TUI's two silent failure modes live (stdout captured by the log redirect — since removed, [ADR-0012](docs/adr/0012-the-log-is-written-per-install-step.md), though "a callback writes nothing to the log" is still the assertion; a bare false `(( ))` aborting a render under `set -e`), so testing them is most of the value. Harness in `test/`, run by `./test/run.sh` and by `.github/workflows/ci.yml`. See [ADR-0008](docs/adr/0008-the-fzf-callbacks-are-the-test-seam.md).
- **Decision (superseded in part by ADR-0010): a Profile row is a macro that stamps its Tools** — toggling it checks its member Tools, and the checked Tools are the only thing that resolves to an install; the Profile row itself is kept as a label for `config.json` provenance. The stamp is one-way and fires only when the visible list holds every member, so an *unstamped* Profile still expands at ENTER and a stamped one does not. This is what makes "presets, not locks" true inside the picker rather than only in principle. The `Profiles` tab is removed — it listed no Tool rows, so the macro could never fire there. A tab switch drops the stamp, because fzf's `reload` clears the selection it made. See [ADR-0009](docs/adr/0009-a-profile-row-is-a-macro-that-stamps-its-tools.md).

- **Decision: the list is the source of truth for a check** — a check lives in `TUI_STATE`, `tui_list` paints the marker (`[x] ◆ go`), and fzf's own selection goes unused. Every interaction records into the state and redraws from it, because fzf clears its selection on every `reload` and the Category tab strip reloads. This deletes all `pos(N)` arithmetic, the stamp's complete-or-label rule, the stamped/unstamped distinction, the startup preselect race, `--multi` and `ctrl-a`, and the "no tools selected" fallback on the interactive path: ENTER installs exactly the state set, an empty set installs nothing, ESC cancels. Supersedes [ADR-0009](docs/adr/0009-a-profile-row-is-a-macro-that-stamps-its-tools.md) in part. See [ADR-0010](docs/adr/0010-the-list-is-the-source-of-truth-for-a-check.md).

- **Decision: the lifecycle is a plain-text transition stream** — the run emits its state and rendering reads it, rather than a screen computing state it alone can see. One `[STEP] <step> | <state>[ | <detail>]` line per change; the state field is one of exactly seven strings and everything that varies per run is detail. `--dry-run` drives the same machine against Install Steps that do nothing — same presence probes, same dependency gate, same emitter, a sleep where the installer's runtime would be — so a dry run is a preview rather than a second guess. `--simulate-fail=<step>` supplies the one thing a dry run cannot find out, and is refused outside it. Colour is dropped when stdout is not a TTY, so nothing has to strip escapes to read a field. See [ADR-0011](docs/adr/0011-the-lifecycle-is-a-plain-text-transition-stream.md).

- **Decision: the install screen reads the transition stream, in a process of its own** — `screen_start` forks a reader with the terminal as its stdout and moves the run's fd 3 onto a pipe to it; the reader keeps a Snapshot, repaints on every Transition and on a timer for the spinner, and finalises when the run says the stream is over, which the run waits for before printing the Summary beneath the frame and reading stdin. The frame is the same pure `render_frame` that `setup.sh __render` calls (#21, ADR-0007). Up when stdout is a terminal and only when the log is open, because a Step's output has to have somewhere else to go; while it is up narration goes to the log alone. Tails are read back off a Step's section in the log by its own markers, not by timing. See [ADR-0013](docs/adr/0013-the-install-screen-reads-the-stream.md).
- **Decision: the log is written per Install Step** — the blanket `exec > >(tee -a "$LOG_FILE") 2>&1` is gone. The run writes its own narration and every Transition to the log in plain text, and each Install Step's output goes there inside a section that names the Step and its exit status — so the log is what you paste into a bug report, and the terminal is free for the install screen to own. A Step's output no longer reaches the terminal at all, which is what the install screen needs before it can own it; a Step that never runs gets no section; the log is opened by `main` alone, so a re-entrant subcommand cannot write to it by accident rather than by remembering not to; and a run whose log cannot be written says so and installs anyway. See [ADR-0012](docs/adr/0012-the-log-is-written-per-install-step.md).

- **Decision: resolution adds a missing prerequisite to the Toolset** — prerequisites are declared data, and a Tool whose prerequisite is neither picked nor already on the machine gets that prerequisite added at resolution, announced on its own line naming the pick that pulled it in. *Missing* is the whole of it: one already on the machine is met, and adding it would drag its Install Step — and every other Tool that Step delivers — into a Toolset nobody asked for. Resolution is the one place the picker's ENTER and every non-interactive flag arrive at, so the two modes cannot resolve the same selection differently. `skipped — unmet dependency` narrows to a prerequisite that was planned and did not land, and a declaration that is circular or ordered after the Tool that needs it is rejected by name rather than closed over. See [ADR-0014](docs/adr/0014-resolution-adds-a-missing-prerequisite-to-the-toolset.md).

- **Decision: the picker shows the closure, and a decline is a pick** — the additions resolution would make are visible in the list (`[+]`) and named in the Selected Toolset panel next to the pick that pulled each one in, before ENTER rather than after the run has started. The closure is derived on every redraw from the same `add_missing_prerequisites` the run calls, so the panel and the run cannot disagree; it is not stamped into the checked set, which stays *what the user picked*. An addition may be unchecked, and that Declined prerequisite travels with the picks into `config.json` and into resolution. Its dependent is not unchecked with it — touching one row must not change two — but is marked unsatisfiable in the panel and reaches `skipped — unmet dependency`, which the run also names before it starts. See [ADR-0015](docs/adr/0015-the-picker-shows-the-closure-and-a-decline-is-a-pick.md).

- **Decision: a Tool reports its version from a declared probe** — `TOOL_VERSION` names the command per Tool, defaulting to `<tool> --version`, and a completed Install Step reports one version per Tool it delivered as the detail of its terminal Transition. `already installed` reports the version found, so a re-run reads as "nothing to do" rather than as instant successes. Nothing is fabricated: a probe that answers no version says `(unknown)`, and the two Tools with genuinely none say `installed`. A dry run runs no probe — an arbitrary declared command line is not a read-only presence check — and reports `(dry run)`, while what is declared rather than probed reads the same either way. This is the single source of version information the spec asks for, which is why the trailing Verification block — a second and disagreeing one — is deleted rather than repaired, closing #10 and #11 with it (#25). See [ADR-0016](docs/adr/0016-a-tool-reports-its-version-from-a-declared-probe.md).

## Open Questions

- **Does `claude-code` need an Install Step?** It has no installer, yet `--all` selects it and the `ai-agents` Profile contains it, so that Profile delivers nothing for it. No longer *silently*: resolution collects it and reports `No Install Step for tool: claude-code` by name, in the dry run and in a real run. Whether it should get an installer is still open. (`c-build` had the same problem; [ADR-0001](docs/adr/0001-full-stack-web-is-a-composite-alias.md) now answers it — narrowed to `cmake` + `pkg-config` and given a real Install Step.)
